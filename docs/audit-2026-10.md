## CRITICAL

### C1. Bodyweight and timed exercises deload a compliant lifter forever [verified]
**Files:** `src/data/recommendations.ts:976` (increase trigger), `:991-1017` (stall), `:1165-1178` (plan clamp)
**Root cause:** `repProgression` only grants an increase when *every* set reaches `repHigh` (`minReps >= exercise.repHigh`), but `buildSetPlan` prescribes a descending drop-off clamped at `repHigh` (12/11/10). A lifter who logs exactly what the plan asks can never satisfy the trigger. After 3 such sessions the stall rule (`repSum(last) <= repSum(oldest)`) fires a deload to `repLow`. Once deloaded, the plan prescribes flat `repLow`, the lifter hits it, the total equals the previous session, and the stall fires again. There is no "same weight" guard because weight is always 0.
**Reproduction (10-week sim, 3×8–12 bodyweight, lifter logs prescribed reps):** weeks 1–4 hold → **weeks 5–10 deload to 8/8/8 every week**. This is the exact `sets × repHigh` bug CLAUDE.md says was fixed — it was fixed only in the loaded engine. Every plank, carry, push-up, pull-up and dip user is affected.
**Fix:** mirror the loaded trigger — increase when the best set ≥ `repHigh` and the credited total ≥ the best prior total; treat "matched the prescribed total" as progress; let the plan prescribe above `repHigh` on `kind: 'increase'`. Add a bodyweight twin of the `week over week — the whole loop` test (`recommendations.test.ts:689`).

### C2. Non-atomic session writes + ghost purge can permanently delete workouts on every device
**Files:** `src/db/database.ts:266-290` (`purgeEmptySessions`), `:373-443` (`applySessionMergePlan`, `writeSessionDoc`); `src/components/WorkoutView.tsx:331-370` (`handleFinish`); `src/App.tsx:120-150`
**Root cause:** three separate write paths leave a session row with zero set logs for a window of time, and `purgeEmptySessions()` treats any such row as a ghost: it deletes it **and records a tombstone** that propagates to the server (`DELETE FROM session_docs`) and every device.
1. **Edit-session save:** `deleteSetLogsForSession(sid)` runs, then N `addSetLog` calls each in its own transaction. An app kill, IDB quota error or exception between them leaves the original session empty → next purge tombstones a real historical workout.
2. **Pull merge:** `applySessionMergePlan` deletes the set logs of replaced sessions in one transaction, then rewrites each doc in separate transactions (`put` session, then `add` sets). Kill mid-way → the *other device's* workout becomes an empty session locally → tombstoned → deleted globally on next push.
3. **New workout:** `createSession` commits before the first `addSetLog`. `purgeEmptySessions` runs from `pullSync`/`pushSync`, which the 60 s interval, the focus handler and `sync()` fire with no mutex. A purge in that window deletes the new session and tombstones it; `completeSession` then throws on `undefined`.
`handleFinish` also has no try/catch: on any failure the `finishing` flag stays true, the button is dead, no feedback, draft not cleared.
**Fix:** (a) write a session and all its sets in **one** readwrite transaction over both stores (chain the `add`s inside the `put` request's `onsuccess`, then `txDone`); do the same for edit (insert new logs before deleting old keys, same tx). (b) Make the purge refuse to tombstone sessions whose `updatedAt`/`startedAt` is younger than a grace period (e.g. 1 h) — a ghost is old by definition. (c) Serialize pull/push/purge through a module-level promise chain in `sync.ts`. (d) Wrap `handleFinish` in try/catch/finally with user-visible error and `setFinishing(false)`. (e) `completeSession` should tolerate a missing row like `touchSession` does.

## HIGH

### H1. In-progress workout drafts are destroyed by ordinary navigation [verified by reading]
**Files:** `src/components/WorkoutView.tsx:190-196`; `src/data/draftSession.ts`; `src/App.tsx:59, 284-350`
- **Single draft slot, overwritten on mount.** `saveDraftSession` runs unconditionally on mount with `sets = {}`. Log 3 sets on Day 2, tap Back (no confirmation), open Day 3 or a quick workout to look → Day 2's draft is overwritten and gone.
- **Quick/shared workouts cannot be resumed.** `quickDay`/`sharedDay` live only in React state; the draft stores `dayId` −1/−2 but not the exercise list, and `findDay` cannot resolve negative ids. An app kill mid-quick-workout (the path advertised to new users) loses every set.
- **A background pull can unmount the open workout.** `backgroundPull` → `startPendingActivation()`/program adoption → `setProgram` → the active `dayId` is gone → `renderView` falls to the dashboard, discarding WorkoutView state.
**Fix:** store the `WorkoutDay` snapshot inside the draft and resume from it (dashboard "Resume unfinished workout" card); never overwrite a draft that `draftHasSets` for a different day without confirmation; confirm on Back when sets are logged; freeze the day for the lifetime of a workout and skip `startPendingActivation` while one is mounted.

### H2. "Finish the week on previous workouts" reactivates blocks the user deliberately ended [verified]
**File:** `src/data/planStore.ts:379-449`
**Root cause:** `deferActiveBlockToNextWeek` cannot distinguish a block auto-closed by `commitActivation` from one the user wrapped up in JourneyView. It takes `mostRecentCompletedBlock`, sets it back to `active`, **deletes its retrospective and `completedAt`**, reinstalls its activation-time program (not the live, possibly edited one), re-anchors weeks, and **unconditionally overwrites any existing `pendingActivation`**.
**Reproduction:** wrap up B1 → 10 days off → activate B2 on a Wednesday → the defer button is offered → B1 is active again, its retrospective gone, a queued pending block vanished.
**Fix:** record how a block was completed (`completedBy: 'activation' | 'user'`, or `replacedBlockId` on the new block) and only allow defer against a block closed by that same activation; refuse when a `pendingActivation` exists; restore the live program, not the block snapshot.

### H3. Admin merge into an exercise the user tombstoned deletes their program slot and library entry [verified]
**Files:** `src/data/merges.ts:120-135`, `:92-112`; `src/data/sync.ts:285-305`
**Root cause:** `applyExerciseMerges` remaps `from → to` without checking `liftlog_deleted_exercises`. The most likely duplicate is "user deleted the catalog exercise and made their own". The survivor written by `mergeLibraryIds` is filtered back out on read, the program slot now points to a tombstoned id, and the next pull's scrub removes it from the day. History is remapped to an id the Exercises screen cannot show.
**Fix:** lift the tombstone on `toId` before remapping (reuse `addToExerciseLibrary`'s logic); add an end-to-end test (only the pure helpers are tested today).

### H4. Program, library and metadata sync is clock-less last-write-wins; edits can be silently reverted
**Files:** `src/data/sync.ts:285-305` (program), `:234-243` (metadata), `worker/sync.ts` (`user_programs`, `exercise_metadata` upserts); `src/App.tsx:120-160`; `src/data/planStore.ts:503-510`
**Root cause:** sessions and the journey carry `updatedAt`; the program, library names and metadata overrides do not. Pull adopts whatever the server has if it differs; push uploads whatever is local. A background pull that was already in flight when `handleUpdateDay` saves lands afterwards and overwrites the edit with the server's old copy, and if it lands before `pushSync` builds its payload the edit is uploaded nowhere. Two devices editing days or metadata lose whichever pulls last. Related, in the journey document: `saveTrainingProfile` bumps the whole-document clock, so a casual "level up" tap on an offline device can reject a newer block activation while still adopting that block's program — plan and program diverge, and `reconcileActiveProgram` only heals an *empty* program.
Also: a user cannot delete their last program day — the worker refuses to store an empty program and pull restores the old one.
**Fix:** add `updatedAt` to the program document and per-exercise `updatedAt` to library/metadata rows (both ends compare before writing); give `profile` its own clock inside `PlanState`; serialize sync and skip pull-adoption while a local change is unpushed.

### H5. Bodyweight stall and bonus-set handling contradict the documented engine [verified]
**File:** `src/data/recommendations.ts:970-971, 996, 1034`
- One bad day = deload: 10/10/10 → 11/11/11 → 10/10/10 at 0 lbs deloads; the same at 100 lbs holds. The loaded engine's best-of-window comparison was never ported.
- A failed bonus set drags the target down: 12/12/12 + a 4th set of 4 → "aim for 5 reps". `minReps`/`avgReps` read all sets with no cap at the programmed count; `credit()` exists for exactly this and is not used here.
**Fix:** run `repProgression` on `credit(last, exercise.sets).sets` and use the best-of-window anchor comparison; share the window logic instead of duplicating it.

### H6. Retrospective adherence is wrong for every phase-gated (sport-support) block [verified]
**File:** `src/data/retrospective.ts:56-60`
`sessionsPlanned = round(program.length × weeks)` ignores `WorkoutDay.phases`. A sprint-tri athlete who attends all 20 schedulable sessions is told "Adherence was the limiter — 20 of 30 planned sessions … worth asking whether the schedule fits your life". Per-muscle weekly sets are likewise under-counted, and the summary promises "the next block adds a set there", which the planner never does on sport-support.
**Fix:** `Σ over block.phases of program.filter(d => dayInPhase(d, phase)).length`; gate the "adds a set" copy on focus.

### H7. Edit-session mode reloads from IndexedDB on every program refresh, discarding unsaved edits
**File:** `src/components/WorkoutView.tsx:254-278`
The loader effect depends on `[existingSessionId, day]`; `day` is a fresh object every `setProgram(getStoredProgram())` (startup line 115 is unconditional; background pulls with `didPull`). The effect re-runs `setSets(groupedSets)` over the user's edits. Fix: depend on `existingSessionId` only, read `day` through a ref.

### H8. Sync failure is invisible, and a failed post-workout push is only retried at the next cold start
**Files:** `src/data/sync.ts:191, 198`; `src/App.tsx:64-150`
401 returns silently from both pull and push; every caller swallows errors. The background tick only *pulls*; it pushes only when a block started/healed. So if the push after Finish fails (offline, or the worker rejects the payload, which CLAUDE.md records happening once), the workout stays local until the PWA is killed and relaunched, which on iOS can be days. A later account switch (`ensureLocalDataOwner`) would wipe it. Fix: a `syncStatus` (last success / last error) surfaced in Settings/Dashboard; re-auth prompt on 401; retry push on the background tick when there is unpushed local data.

## MEDIUM

### M1. Worker: error responses leak stack traces; push validation has gaps; push is not atomic
**Files:** `worker/index.ts:20-23`; `worker/sync.ts:252-305, 320-520`
- `Response.json({ error, detail: message })` returns `err.stack` to the client on every 500. Log it, return a generic body.
- `exerciseMuscles`/`exerciseDetails` are not validated at all (a non-array value throws `.map` → 500); `completedAt` is not type-checked (a string lands in an INTEGER column and comes back as a string, breaking duration math); `program` is `unknown` with no size bound (the plan has `MAX_PLAN_BYTES`, the program does not).
- `env.DB.batch` is called per 100-statement chunk, each its own transaction. Tombstone inserts and `session_docs` deletes land in early chunks; a later chunk failing leaves a partially applied push.
- Every push issues `DELETE FROM user_exercises`/`exercise_metadata` for **every** tombstone (user + legacy app-wide set) — 2×N statements per push regardless of need.

### M2. Every pull and push moves the entire history, every 60 seconds
**Files:** `src/App.tsx:138`; `worker/sync.ts` (`pull`, `push`)
There is no cursor, ETag or `since`. A multi-year user (≈800 sessions, ≈16k sets) downloads ≈1 MB JSON per pull; with the 60 s tick while the app is open that is tens of MB per hour on cellular, and every push re-upserts every session document. CLAUDE.md argues payloads are "tiny for a personal training log"; they are not tiny at 60 s cadence over years. Fix: `If-None-Match`/`Last-Modified` on pull (cheap: a per-user `max(updated_at)`), and a push that sends only documents with `updatedAt > lastPushedAt`.

### M3. No CI, lint failing, build does not gate on lint
Nothing prevents a red lint or failing test from auto-deploying to Cloudflare Pages. The two current errors (`DayEditView.tsx:49`, `PlanSetupView.tsx:312`, `Date.now()` in render) are real: memoized suggestions drift across renders, and `PlanSetupView.suggestionsFor` runs the full substitution ranking twice per exercise per render. Add a GitHub Actions workflow running typecheck + lint + test on PRs; hoist `now` into state.

### M4. The "goal-weighted composite" stall verdict never changes a recommendation [verified, 360,000 random windows, 0 flips]
**File:** `src/data/recommendations.ts:857-874`
Both `flat` and `stalled` require `prEvents === 0`, which already implies every signal ≤ 0 after `deadband`; the max possible score (0.175, sport-support hold bonus) is below both thresholds. `stalled ≡ flat ≡ sameWeight && prEvents === 0` for every goal and training age. The `progress.ts` screen can still say "steady" while the engine deloads. Either make the verdict depend on the score or remove the call and document the real rule.

### M5. Weekly rate cap decided by floating-point noise [verified]
**File:** `src/data/recommendations.ts:569, 743`
`100 × 1.1 === 110.00000000000001`, so a beginner at 110 after a 100→110 jump three days ago is *not* caught by `weight >= ceiling` and goes to 115 — 15 % in a week against a documented 10 % cap. Snap the ceiling to the increment or compare with epsilon.

### M6. "Edit Session" on a quick or shared workout dead-ends on the dashboard
**Files:** `src/components/HistoryView.tsx:141`; `src/App.tsx:170-190`
`onEditSession(session.id, session.dayId)` with dayId −1/−2 → `findDay` misses → dashboard renders. The button is shown and silently does the wrong thing. Build the edit `day` from the session's logged exercises when the id is not in the program.

### M7. Free-text injury notes become hard exercise bans on benign input [verified]
**File:** `src/data/planner.ts:140-160`
No negation handling and the `back` rule matches "back squat": *"my shoulder hurts when I do back squats"* bans Dip, Vertical Press, Hip Hinge **and Squat**; *"no knee problems, but my elbow hurts"* bans squats; *"knee surgery 10 years ago, fully recovered"* bans squats. This is the Tier-1 hard-constraint path. Exclude lift names, handle `no|without|recovered|fully`, or move injuries to structured chips like niggles.

### M8. Sport-support template defects [verified]
**File:** `src/data/sports.ts:85-86, 784-789, 826-851`; `src/data/planner.ts:856-970`
- `main: true` is overloaded: it both selects the event rep range and protects from trimming, so the step-up and chin-up get 4×4–6 on sprint/olympic/5k/10k plans where the docs promise 3×6–8 / 3×6–10.
- `'intro'` is missing from `BUILD_PHASES`/`THROUGH_MAINTENANCE`, so intro weeks schedule only the Max Strength day — the unilateral, durability and power work gets its first exposure in week 3 at full load, defeating the intro week's purpose.
- `sports.ts` caps on direct sets with a floor of 3 for main slots; `planner.ts` re-caps on direct + 0.5×secondary with a floor of 2 and no knowledge of `main`. The documented hamstring emphasis is added by one and removed by the other.

### M9. A custom exercise promotes a two-week novice to intermediate [verified]
**Files:** `src/data/experience.ts:272-289`; `src/data/exercises.ts:300-303`
`difficultyFor` defaults unknown ids to `'intermediate'`; 8 sessions of `my-weird-band-thing-17…` in 16 days → intermediate, which ratchets and removes the beginner safety net (≥8 reps, split cap, skill gate). Count only ids with explicit catalog difficulty.

### M10. `startOfWeek` yields a phantom week in zones whose DST transition is at 00:00 [verified: America/Santiago, Havana, Asia/Beirut]
**File:** `src/data/program.ts:170-176`
`setHours(0,0,0,0)` on the spring-forward Sunday gives 01:00 and `setDate(-6)` lands on Monday 01:00 — a different key from the rest of the week. `thisWeekVolume` and the weekly bar disagree; coach week filtering drops that Sunday. Construct the Monday with `new Date(y, m, d - offset)` instead.

### M11. Intra-session "rep PRs" [verified]
**File:** `src/data/progress.ts:137-149`
`repMap` is updated inside the loop over the same session's sets, so set 2 beating set 1 is a PR — including on the first session ever at a never-lifted weight. Inflates highlights and `prEvents` (a stalled lift reads "steady"). Compute session bests first, then compare against the pre-session map.

### M12. Legacy `'Press'` override and custom-to-custom merges lose classification [verified]
**Files:** `src/data/exercises.ts:453-508`; `src/data/merges.ts:132`
A stored bare `'Press'` on a catalog *overhead* press resolves to Horizontal because `normalizeOverride` has no id to consult the catalog with. Merging custom A (override: Chest) into custom B (no override) deletes A's metadata and leaves B unclassified. Pass the id into normalization; copy the from-override onto a survivor that has none.

### M13. Prescription UI inconsistencies
**Files:** `src/components/ExerciseCard.tsx:71-78, 212-214`; `src/components/WorkoutView.tsx:230-252`; `src/data/recommendations.ts:1181-1195`
- Timed exercises: the chip renders `${targetReps} reps` for a 36 s plank; the goal line still demands `sets × repHigh` total seconds the plan can never add up to.
- `plan !== appliedPlan` resets every card's `workingWeight` whenever *any* plan object is rebuilt — adding an exercise mid-workout or any background `setProgram` snaps the lifter's chosen weight back to the recommendation, and the next one-tap log records the wrong load. Memoize per exercise id or compare content.

### M14. No error boundary; a render-time throw white-screens a workout
**Files:** `src/main.tsx`; `src/components/ShareWorkoutModal.tsx:212-218`
`qr.make()` throws `'code length overflow'` inside `useMemo` for a long day (verified: 30 × 80-char names → 3763-char URL throws); there is no `ErrorBoundary`, so Share on a large day unmounts the tree. Add a top-level boundary that preserves the draft; catch and show "too large to share"; cap the encoder to QR capacity.

### M15. Service-worker updates never reach a resident iOS PWA
**Files:** `vite.config.ts:17-47`; `src/main.tsx:12-20`
`registerType: 'autoUpdate'` installs the new SW immediately but nothing listens for `controllerchange` or reloads; `reg.update()` only speeds up install. With auto-deploy on every push, an installed PWA runs stale JS against a newer worker for days — the client/server contract mismatch would present as H8's silent failure. Add a "update ready — reload" toast (never during a workout) or `registerType: 'prompt'`.

### M16. Pending-activation edge cases [verified]
**File:** `src/data/planStore.ts:153-176, 252-262, 342`
A future start with nothing running installs immediately (active block, `startDate` weeks out, `getActivePhase()` null, phase-gated days all visible). Wrapping up the running block while a pending one exists orphans it. A mid-week start while a block runs installs *now* although the button says it starts later. Make the rule one-directional: pending whenever `anchor > now`.

### M17. Analytics performance traps [measured]
**Files:** `src/data/metrics.ts:59-61`; `src/data/exercises.ts:515-534`; `src/data/analytics.ts:308-331`
Two years of history: `computeMetrics` 426 ms, of which `toLocaleDateString` is dominant (6000 calls = 875 ms vs 7.6 ms with one cached `Intl.DateTimeFormat`). `getExerciseMeta` re-parses and re-normalizes the whole override blob on every call; `headSetTotals` calls it per set log (1.7 s / 8,944 localStorage reads). `applyExerciseMerges` does a full set-log `getAll()` every 60 s once any merge exists.

### M18. Advanced lifters' stall detection is disabled by the 4-session history cap [verified]
**Files:** `src/components/WorkoutView.tsx:94`; `src/data/progression.ts:188`
`stallWindowFor('advanced')` is 4 and WorkoutView passes at most 4 sessions, dropping late-slot ones first; one shifted session → no stall check at all. `bestWorkAt` likewise only sees 3 prior sessions, so "most work ever at this load" means "in the last 3 sessions". Pass `stallWindowFor(experience) + 2` or all sessions at the working weight.
